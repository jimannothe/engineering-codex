# Engineering Codex Architecture

## Purpose

Engineering Codex is the headquarters.

It coordinates the long-term system, but large software projects should graduate into their own repositories.

## Repository Layout

Engineering Codex should hold:

- mission and vision
- curriculum and academy structure
- current context
- roadmap and backlog
- weekly reviews
- knowledge base
- project index
- templates and methodologies
- links to external repositories

## Project Lifecycle

Every meaningful project should follow the same flow:

Idea
Research
Planning
Prototype
Project
Documentation
Portfolio
Reflection

## Portfolio Structure

The GitHub portfolio should eventually contain repositories such as:

- Engineering Codex
- Reliability Lab
- Validation Tools
- Digital Systems Lab
- Home Lab
- AI Research Assistant
- C++ Performance Notebook
- Embedded Lab
- Robotics Lab
- Printer Restoration
- Quadcopter
- Quant Lab

The Codex acts as the central coordinator for all of them.

## Operating Rules

- Keep WIP limited to one primary project, one learning track, and one maintenance task.
- Keep `CURRENT_CONTEXT.md` explicit enough that work can resume after interruption.
- Put a date at the top of `CURRENT_CONTEXT.md` and overwrite it as state changes.
- Prefer documentation, code, experiments, or tools over undocumented progress.
- Use the smallest effective artifact for the job.
- Promote stable work into the roadmap, projects, or weekly review notes.

## Success Criteria

Success is not measured by how many technologies are touched.

Success is measured by:

- projects completed
- systems built
- knowledge retained
- documentation produced
- portfolio quality
- engineering judgment

## Weekly Rhythm

Keep work moving in a simple weekly loop:

- plan
- build
- document
- review

## Recursive Principle

Engineering Codex is itself an engineering project.

It should use its own standards, document its own evolution, and improve itself over time through automation and AI assistance.
